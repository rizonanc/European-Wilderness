# 2.9.0 — приоритеты inference, профилирование и входные буферы

31 октября 2026. Minecraft 1.21.11 / Fabric / Java 21 / Windows DirectML.
Реализованы три согласованных изменения без замены моделей и формата мира.

## Общая очередь и объединённые запросы

Один исполнитель по-прежнему обслуживает весь нейросетевой пайплайн. В очереди
теперь три приоритета: FOREGROUND — игровые запросы; NEAR — подготовка ближайших
областей; DISTANT — дальний LOD. Задания одного приоритета сохраняют порядок
поступления. Новое важное задание обгоняет ожидающие менее важные задания.
Начатый нативный вызов не прерывается, поэтому игровой запрос всё ещё может
дождаться уже выполняющегося расчёта одного региона.

У каждого объединённого запроса TerrainRepository есть общий объект спроса.
Если игровой чанк начинает ждать тайл, первоначально заказанный дальним LOD,
приоритет этого же задания повышается. Повторная генерация не запускается.
Повышение работает и до привязки задания к очереди, и после неё. Приоритет
не понижается при появлении новых фоновых читателей.

Прерывание одного ожидающего читателя больше не удаляет из реестра ещё
выполняющийся общий запрос. Задания завершённого WorldSession проверяются
перед выполнением и пропускаются. Проверки активности перед сохранением
данных сохранены. Инициализация/смена seed остаются в единственном исполнителе.

## Входные тензоры ONNX

Для каждого экземпляра модели добавлен кеш прямых CPU-буферов и соответствующих
OnnxTensor. При совпадении имени и формы входа буфер заполняется новыми значениями,
а нативный входной тензор используется повторно. Изменение формы пересоздаёт
соответствующий вход. Сохраняется не более 16 имён и 8 MiB входных данных на
экземпляр модели; превышение бюджета обслуживается временным тензором,
который закрывается после вызова. Проверяются формы, размеры и дубликаты имён.

Один экземпляр модели сериализует вызовы Run и закрытие, поэтому активный
вход не может быть перезаписан другим вызовом. Временные ресурсы и результат
закрываются до повторного использования входов. Закрытие модели освобождает
кеш тензоров. Модели используют прежние FP32-значения, ONNX-графы, веса,
размеры окон, генератор шума, батчи и execution provider.

Это переиспользование CPU-входов. Передача CPU↔GPU execution provider остаётся;
полноценный GPU I/O Binding не добавлен. Выходные массивы остаются отдельными,
поскольку пайплайн хранит результаты после возврата Run.

## Диагностика

В `/td-stats` добавлены:

- Ожидание и исполнение отдельно по FOREGROUND / NEAR / DISTANT, длина очереди,
  число повышений приоритета и пропущенных заданий устаревшего мира.
- Для каждой модели: `sessionCreate`, `sessionClose` при смене GPU-слота,
  `slotWait`, `inputPrepare`, `runWall`, `outputCopy`.
- Для входов: созданные и повторно использованные тензоры, размер удерживаемого
  кеша и объём скопированных входных значений.

`runWall` — время синхронного Session.run, включая работу execution provider и
его передачи данных, а не чистое время GPU-ядер. `sessionClose` у новой модели
описывает выгрузку предыдущего владельца при переходе к ней. Счётчики моделей
охватывают процесс игры; для сравнения нужны дельты двух замеров в одном мире.
Существующие измерения диска, водного планирования, кешей, кадров и LOD сохранены.
Политика offload моделей и настройки пользователя не менялись.

## Проверки

`gradlew build exportQaRuntime`: 208 тестов без ошибок и пропусков. Новые тесты
проверяют порядок приоритетов, повышение общего тайла без дублирования,
пропуск устаревших/отменённых заданий, восстановление контекста после исключения
и сохранение выполняющегося запроса после прерывания читателя.

Нативные CPU-тесты используют собственный маленький ONNX Identity-граф
(IR8/opset13) с динамическим float-вектором. Подтверждены обновление данных
при повторном использовании одного тензора, побитовое сохранение значений
(включая -0 и NaN), смена формы, временные входы при превышении бюджета,
восстановление после ошибки и запрет повторной выдачи активного буфера.

Отдельный `OnnxBufferProbe`: 327680 float-значений, 64 вызова на вариант,
три прогона с чередованием порядка после прогрева. Создания входного тензора:
64 → 1, ещё 63 использования кеша. Контрольные суммы совпали. Время старого /
нового варианта в финальном прогоне: 49.57/28.89, 38.31/23.32, 39.66/20.43 мс. Java-выделения
остались около 84 MB на вариант: копирование выхода доминирует и сохраняется.
Результат показывает снижение затрат создания входов в данном CPU-тесте,
а не ускорение генерации мира или DirectML в такое же число раз.

Полные модели Terrain Diffusion и игровой FPS на новой сборке ещё не сравнивались.
Артефактный контроль проверяет неизменность WorldPipeline, моделей/загрузчика,
профиля генерации, геометрии воды/деревьев и прежнего моста LOD.
Установленный JAR, конфиги, сохранения и кеш игры при разработке не заменялись.

## Какие идеи остаются экспериментами

Предсказание движения, RAM/дисковый кеш, объединение запросов, базовые батчи
и кадровый governor уже существовали. Этот пакет дополняет их приоритетами
и измерениями. FP16, изменение inference-разрешения, фиксация динамических
размеров графа и увеличение батчей не включались. Отдельный грубый дальний LOD
для быстрого горизонта на 2048 чанков ещё требует реализации.

CPU-подготовка ленивых тензоров остаётся в единственном исполнителе с их
кешами. Сохранение raw-тайла выполняется вне inference-исполнителя и может
перекрываться со следующим уже поставленным расчётом. Более глубокое перекрытие
CPU/GPU и удержание дополнительных моделей в VRAM следует выбирать по новым
измерениям; этот пакет не создаёт параллельные Run для одной DirectML-сессии.

После установки проверить тот же маршрут и два `/td-stats` с интервалом
60 секунд. Для радиуса 2048 чанков сохраняется `/td-voxy start 32768`.
Сравнивать время ожидания FOREGROUND, raw-тайлы/ядра/порции LOD и стадии
каждой модели, отдельно от времени кадров и стоимости первого прогрева.
